お仕事で関わっているTAIANで、開発環境でのUI反映が遅いという問題があったので、その背景と解決までの経緯をまとめます。

## UI リロード平均時間：20s → 2s 🚀

本稿では、Rails + esbuild のローカル開発で「フロント更新後の UI 反映が遅い」原因を洗い出し、app/assets/builds の直接参照と Foreman によるプロセス統合、さらに初回ロードやデータ再取得の最適化（N+1解消）で、体感レスポンスを 10 倍改善した方法を解説します。

## 1. なぜ遅かったのか（具体）

- esbuild は app/assets/builds に bundle.js / bundle.css を出力
- Rails の既定探索パスは app/assets, lib/assets, vendor/assets などで、builds は探索外
- 結果として、Sprockets/パイプラインが出力物を直接解決できず、反映まで待ち時間が増大

## 2. プロセス統合（Foreman）

動機：Rails と esbuild を同一プロセス管理下に置くことで、環境・TTY・ログを統一し、跨コンテナのファイル監視や起動連携のオーバーヘッドを削減

- docker-compose.yml で Foreman を導入し、Procfile.dev によって Rails（web）と esbuild を同一プロセス管理下で並行起動。独立した esbuild サービスを削除し、協調コストを削減しました。

## 3. データ取得に関して N+1 の懸念を解決（preload で一括）

結論：一覧描画で参照する関連は ‎`preload` で事前ロードして、ビューアクセス時の追加 SQL をゼロにして、UIリロード時のデータ再取得コストを削減し、表示を高速化しました。

## 4. 計測条件

- 環境：ローカル開発（例：Mac/Chrome、Rails 7 + esbuild）
- シナリオ：JS 1ファイル編集 → ブラウザで UI 反映確認
- 状態：温状態の平均（n=10）。冷起動は参考値
- 結果：20s → 2s（温）／ 冷起動は 35s → 12s（例）

## 注意事項／学んだこと

- Foreman の扱い：公式ドキュメントにある通り、Ruby プロジェクトの Gemfile には foreman を記載しない。代わりに、開発用にはシステムレベル（またはコンテナ側）でインストールし、`Procfile.dev` を入口に統合する。

![](https://storage.googleapis.com/zenn-user-upload/cc605e4e2b14-20260113.png)

参考資料：https://github.com/ddollar/foreman

> Ruby users should take care not to install foreman in their project's Gemfile. See this [wiki article](https://github.com/ddollar/foreman/wiki/Don't-Bundle-Foreman) for more details.

## まとめ

アセット探索パスの整合、Foreman によるプロセス統合、そして N+1 回避で、Rails × esbuild の開発ループは安定して高速化できます。最小 diff → ローカル検証 → 計測記録の順で導入し、待ち時間の原因を一つずつ潰すことで、チームの反復速度と安全性を両立できます。テンプレートや設定例が必要であれば、コメントでリクエストしてください。
