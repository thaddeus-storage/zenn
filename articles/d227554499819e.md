## はじめに

ファイルアップロードで `timeout` が返ったとき、それは必ずアップロードの失敗を意味するわけではない。
クライアント側の `timeout` は、制限時間内にレスポンスを受け取れなかったことを示す。
しかし、その時点でサーバー側の処理が失敗したとは限らない。

Google Drive API のような外部ストレージ API では、リクエスト本文がすでに Google Drive に届き、ファイル作成まで完了している可能性がある。
失われたのはアップロードそのものではなく、最後のレスポンスだけかもしれない。

この状態で単純に retry すると、同じファイルを重複して作成したり、成功したアップロードを失敗として記録したりする。
大きなファイルを扱うアップロードでは、`timeout` を失敗ではなく「結果が分からない状態」として扱う必要がある。
そのために使うのが、Google Drive API の **Resumable Upload** である。

## Multipart Upload の境界

Google Drive API には複数のアップロード方式がある。

- **`media`**：メタデータを送らず、ファイル本文だけを送る方式
- **`multipart`**：メタデータとファイル本文を一つのリクエストで送る方式
- **`resumable`**：アップロードセッションを作成し、そのセッションに対してファイル本文を送る方式

`uploadType=multipart` は扱いやすい。
メタデータとファイル本文を一つのリクエストにまとめて送れるからである。

```http
POST /upload/drive/v3/files?uploadType=multipart
Content-Type: multipart/related; boundary=...
```

この方式は、小さなファイルには向いている。
Google Drive API のドキュメントでも、multipart upload は小さなファイルをメタデータと一緒に送る方式として説明されている。

しかし、multipart upload は一回のリクエストで完結する。
クライアント側で `timeout` が起きたあと、そのリクエストを Google Drive がどこまで処理したかを確認するためのセッションがない。

このときローカルで分かるのは、「リクエストが失敗したように見える」ということだけである。
リモート側でアップロードが完了したのか、途中まで受信されたのか、そもそも届いていないのかは分からない。
この曖昧さが、大きなファイルアップロードで multipart upload を扱いにくくする。

## Resumable Upload の流れ

Resumable Upload は、アップロードを二つの段階に分ける。
最初に、アップロードセッションを作成する。

```http
POST /upload/drive/v3/files?uploadType=resumable
Content-Type: application/json; charset=UTF-8
X-Upload-Content-Type: application/octet-stream
X-Upload-Content-Length: <file_size>
```

リクエスト本文にはファイルのメタデータを入れる。

```json
{
  "name": "video.mp4",
  "parents": ["<folder_id>"]
}
```

Google Drive がセッションの作成に成功すると、レスポンスの `Location` header に session URL が返る。

```http
HTTP/1.1 200 OK
Location: https://www.googleapis.com/upload/drive/v3/files?uploadType=resumable&upload_id=...
```

以降のファイル本文のアップロードは、この session URL に対して行う。
二回目以降のリクエストを `/upload/drive/v3/files` に送らない。
session URL は、ファイル本文を送り、アップロード状態を問い合わせるための URL である。

## Content-Range で chunk を送る

ファイル本文は、session URL に `PUT` リクエストで送る。
一回で送ってもよいが、大きなファイルでは chunk に分けて送るほうが扱いやすい。

ここでは 8 MiB を chunk size とする。
Google Drive API では、最後の chunk を除き、chunk size を 256 KiB の倍数にする必要がある。
8 MiB は 256 KiB の倍数なので、この条件を満たす。

```js
const chunkSize = 8 * 1024 * 1024; // 8388608 bytes
```

chunk upload では、`Content-Range` header で今回送る byte range を示す。

```http
PUT <session_url>
Content-Type: application/octet-stream
Content-Length: 8388608
Content-Range: bytes 0-8388607/20971520
```

`Content-Range` は次の形式を持つ。

```http
Content-Range: bytes <start>-<end>/<total>
```

`end` は inclusive である。
したがって、`bytes 0-8388607/20971520` は、全体 20 MiB のファイルのうち、先頭 8 MiB を送るという意味になる。

## 308 Resume Incomplete を読む

アップロードがまだ完了していない場合、Google Drive は `308 Resume Incomplete` を返す。

```http
HTTP/1.1 308 Resume Incomplete
Range: bytes=0-8388607
```

`Range` header は、Google Drive が受信済みの byte range を示す。
この例では、`0` から `8388607` byte まで受信済みである。
次のアップロードは `8388608` byte から始める。

```http
Content-Range: bytes 8388608-16777215/20971520
```

ここでローカルの送信済み byte 数を基準にしない。
基準にするのは、Google Drive が返した `Range` header である。
前回リクエストの本文をすべて送信したように見えても、そのすべてがサーバー側で確認されたとは限らない。

Google Drive が確認した位置から再開することで、ローカル状態とリモート状態のずれを避けられる。
アップロードが完了すると、Google Drive は `200 OK` または `201 Created` を返す。
このレスポンスを受け取った時点で、ファイルアップロードは完了したと判断できる。

## Timeout 後は失敗にしない

Resumable Upload で効くのは、timeout 後の扱いである。
chunk upload 中に transport timeout が発生したとき、すぐにアップロードを失敗として扱うわけにはいかない。
その chunk が Google Drive 側では完了している可能性があるからである。

この場合は、同じ session URL に空の `PUT` リクエストを送り、アップロード状態を問い合わせる。

```http
PUT <session_url>
Content-Length: 0
Content-Range: */<total_size>
```

レスポンスによって次の処理を決める。

- `200` または `201`：アップロードは完了している
- `308`：アップロードは未完了である
- `404`：セッションが期限切れである
- その他の error：通常の API error として扱う

`200` または `201` が返った場合、timeout した chunk request は Google Drive 側では完了していたと判断できる。
`308` が返った場合は、`Range` header を読み、Google Drive が確認済みの byte range からアップロードを再開する。
この仕組みによって、「アップロードが成功したか分からない」という曖昧な状態を、「サーバーに確認して続きから再開できる」状態に変えられる。

## 実装上の分岐

実装では、処理を次のように分けると整理しやすい。

```js
async function uploadWithResumableSession(file) {
  const sessionUrl = await createResumableUploadSession(file);
  const totalSize = file.size;

  let offset = 0;

  while (offset < totalSize) {
    try {
      const response = await uploadChunk(sessionUrl, file, offset);

      if (response.status === 200 || response.status === 201) {
        return response;
      }

      if (response.status === 308) {
        offset = nextOffsetFromRange(response.headers.get("Range"));
        continue;
      }

      throw new Error(`Unexpected upload response: ${response.status}`);
    } catch (error) {
      if (!isTransportTimeout(error)) {
        throw error;
      }

      const statusResponse = await queryUploadStatus(sessionUrl, totalSize);

      if (statusResponse.status === 200 || statusResponse.status === 201) {
        return statusResponse;
      }

      if (statusResponse.status === 308) {
        offset = nextOffsetFromRange(statusResponse.headers.get("Range"));
        continue;
      }

      if (statusResponse.status === 404) {
        return uploadWithResumableSession(file);
      }

      throw new Error(`Unexpected status response: ${statusResponse.status}`);
    }
  }
}
```

この流れで保持する状態は多くない。

- **session URL**：`Location` header から取得した upload URL
- **total size**：ファイル全体の byte size
- **current offset**：次に送る byte offset
- **confirmed range**：Google Drive が受信済みとして返した byte range

実装の中心は、chunk を送ることではない。
Google Drive が確認した offset を読み、その位置から再開することである。

`Range` header から次の offset を求める処理は、次のように書ける。

```js
function nextOffsetFromRange(rangeHeader) {
  if (!rangeHeader) {
    return 0;
  }

  const match = rangeHeader.match(/bytes=0-(\d+)$/);

  if (!match) {
    return 0;
  }

  return Number(match[1]) + 1;
}
```

## 実装で落としやすい点

session URL は絶対 URL として返る。
HTTP client に base URL を設定している場合、session URL にさらに base URL を足さないようにする。

`Range: bytes=0-42` は、43 byte を受信済みという意味である。
次の offset は `42` ではなく `43` になる。

`308` response に `Range` header がない場合、受信済みの byte range を確認できていない。
この場合は、Google Drive がまだ byte を受信していないものとして扱う。

resumable session URI は永続的な URL ではない。
Google Drive API のドキュメントでは、session URI は一週間で期限切れになると説明されている。
期限切れの場合は、新しい session を作成し、アップロードをやり直す。

## 小さな変更ではなく protocol の変更

multipart upload から resumable upload への変更は、リクエスト本文の作り方を変えるだけではない。
失敗時の考え方を変える変更である。

multipart upload では、timeout 後にリモート状態を確認できない。
resumable upload では、session URL に対して status を問い合わせ、Google Drive が確認した位置から再開できる。
そのため、retry の前にリモート状態を確認する流れを作れる。

```js
await queryUploadStatus(sessionUrl, totalSize);
await resumeFromConfirmedOffset(sessionUrl, file);
```

ファイルアップロードの `timeout` は、失敗ではなく結果不明である。
大きなファイルを Google Drive API にアップロードする処理では、この前提で protocol を選ぶ必要がある。

Resumable Upload の価値は、単にファイルを chunk に分けられることではない。
session、offset、`Range`、status query を使って、結果不明の upload を確認可能な状態に戻せることにある。
